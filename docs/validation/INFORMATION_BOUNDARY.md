# Information boundary

The simulator is allowed to know the release schedule. It is the ground-truth environment. The policy is not.

`Observation` has these fields: `time`, `vehicles`, `released_open`, `accepted`, `completed`, `rejected`, `in_service`, `deferred`. There is no hidden-request field. `tests/test_replay_and_episode.py` checks the dataclass fields and checks that two controllers given the same observation return the same planned customers.

`DynamicScenario.hidden_at` exists for tests of the generator. `EventTriggeredMPC.decide` does not take a scenario.

## Release mechanisms

Version `dynamic-release-v1`.

- `indexed_stagger`: sorted ids at `0, step, 2 step, ...`. The seed is not used to move times. This is the development scenario, with step 40 on `c101C5`.
- `uniform`: independent `Uniform(0, release_horizon)` draws. The same seed repeats. A different seed changes the times. Nothing is clipped to an offline route.
- `lead_time`: each customer is announced a uniform lead before `ready`, clipped only at time 0. Feasibility is not consulted.
- `poisson_pool`: a non-homogeneous Poisson process is generated by thinning on the piecewise rates, then epochs are paired with a random permutation of the finite pool. Extra epochs are dropped. Customers without an epoch are not released. This is not an infinite arrival process and not a feasibility filter.

`independent_parent_scenarios` builds one uniform scenario per parent instance. Two seeds on `toy-easy` are repeated scenarios of one geometry. `toy-easy` and `toy-impossible_window` are different geometries; the test checks that customer `C2` is not at the same coordinate.

## Episode check

On the easy toy, `C3` is released at time 30. Every decision before time 30 excludes `C3` from the accepted, rejected, deferred, and planned sets. The development log releases `C12` at time 40, after `v1` has already arrived at `C100`. The destination of that completed travel is `C100`.
